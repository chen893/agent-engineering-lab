已展示的理解：知道用 PID 检查判断进程是否回收；知道通过 settled 防止 error/close 重复结束；知道非零退出与取消应映射 isError=true，并保留 content/details。PID 回答尚未指定输入、同步时点与断言，不能据此记为完整验证设计通过。

需校正：

1. 当前取消不会 throw：Agent.abort 调用本次运行的 AbortController.abort（agent.ts:391），signal 由 runWithLifecycle/runAgentLoop 传给 executePreparedToolCall，再到工具 execute/runProcess。abort 监听器注册在 runner，不在 agent-loop；onAbort 标记 aborted 并 kill，随后 close 刷新输出并 resolve aborted。process-tool 返回 content/details/isError，agent-loop 走 try 的正常返回分支。启动失败才由 runner reject，经工具传播至该 catch。
2. settled 是本次调用进入终结处理、防止重复处理的标志，不是独立的资源回收证据。error 分支未等 close 就设为 true；close 分支也先设为 true 再刷解码器、resolve。运行中取消的回收依据是等待 close 与 PID 检查，不能用 kill 或 settled 赋值单独证明。aborted 表示本次处理已接收取消，不能等同进程已停止。AbortController 与其 signal 应区分命名。
3. “再次进入模型流再以 aborted 结束”在当前无 finishTurn 干预的路径上有依据；但 streamAssistantResponse 只是把 signal 传给 StreamFn，并不自动把任意 mock 的结果改成 aborted。应写明此条件，且区分 agent_end 和后续 finishRun/waitForIdle 的真正空闲。用户尚未提供实际读过的位置索引。
4. 成功返回示例中顶层 exitCode 不属于 AgentToolResult 的标准字段；退出码在 details.exitCode，content 中也表达给模型。当前实际工具实现已满足，不需要因回答示例修改实现。
5. “用 PID 检查”是验证思路，尚缺一组可执行的输入、READY/事件同步取消时点与结果预期。按原 README 补关键场景即可，不增加新契约；不代写目标为验证设计的正式测试。
