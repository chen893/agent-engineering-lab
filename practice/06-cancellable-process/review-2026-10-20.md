## 结论

runner 的直接 spawn、前置取消、取消时 kill 后等待 close、分流 UTF-8 解码及 abort 监听器清理思路符合当前契约。此次有限运行检查未发现契约内缺陷，不等于完整验收。

pi 内的 process-tool 存在以下问题：

1. execute 直接返回 RunResult，缺少 AgentToolResult 必需的 content/details；定向类型检查报告 TS2322。
2. 非零退出未设置 isError；当前 Agent 通过 result.isError 判断错误。
3. 取消时 throw Error("aborted")，Agent 会转成通用错误结果，无法保留本题要求的 RunResult details 及已收集输出。应返回带 isError 的结构化工具结果；启动失败仍可抛出。
4. 工具名 process 与契约中的 run_process 不符，测试模型返回 run_process 时无法匹配。
5. 工厂未指定第二个泛型 RunResult；ToolDefinition/扩展上下文/wrapper 对本题直接接入 Agent 并非必需。当前 wrapper 的参数 schema 使用 any，工厂返回标注不能替代边界检查。
6. processToolConfig 未使用；definition 没设置 prompt 元数据，Object.assign 还把 promptGuidelines 赋给 promptSnippet。迁移时建议省去这些本题不使用的配置。

validateProcessInput 只检查数组，没检查元素；真实 Agent 会先按 schema 校验，本题正常数据契约下这不是新增验收项，也无需另造校验层。
