# 下一任务：固定预算下裁剪对话历史

对应实践入口第 4 项，Q011、Q012。用户已完成多次实现尝试；2026-10-17 按用户要求转为 AI 辅助局部修复，保留用户反向扫描与切分点算法。本轮按连续工具批次契约验收，2026-10-17 实际运行 14/14 项通过；测试与局部修复由 AI 提供，不能据此认定用户独立完成了修复。

先收尾并发任务的配置检查：合法值必须是正整数；当前 1.5、NaN 仍失败，Infinity 尚未实际运行验证。不要把核心调度通过等同于全部验收通过。

## 为什么选它

你已练过工具结果关联和异步调度，本次换一个能力维度：在资源预算下维护跨消息依赖，并明确哪些信息能丢、哪些不能丢。该能力对应 Agent 每次请求模型前的上下文整理。这里不接真实模型，不宣称与 pi 的压缩实现相同。

## 需求与范围

实现纯函数 `fitContext(messages, budget)`，返回裁剪后的消息和删除信息。接口与内部表示先由你提出，助手再集中审查；本次不预设完整类型体系。

输入是完整对话历史，包含 system、user、assistant、tool。assistant 可以包含零个或多个工具调用；每条 tool 结果通过调用 ID 对应。输入保证 ID 唯一、每个调用都有一个结果，且没有尚未结束的调用。无需这轮实现畸形历史校验。

本轮采用串行、连续批次前提：每条含工具调用的 assistant 消息之后，紧跟其对应的全部 tool 结果消息。允许同一批次的多个结果合并为一条 tool 消息；批次内部不穿插 system、user 或另一条 assistant。跨批次交错结果和批次内插入其他角色均不属于本轮输入契约，不要求校验或修复。

预算固定按以下方式计算：

```ts
const cost = (messages: unknown[]) => JSON.stringify(messages).length;
```

这是序列化后的 JavaScript 字符串长度，不是真实 token 数。按用户最新要求精确计入外层数组的括号和逗号；每条消息只序列化一次，整体成本为 `2 + 消息长度和 + Math.max(0, 消息数 - 1)`。元数据和工具参数也计入预算，输入为普通 JSON 数据（不包含自定义 toJSON 或有副作用的 getter）；budget 为非负整数。

## 验收标准

1. 已在预算内时保留全部消息，不修改调用方输入。
2. 所有 system 消息和最后一条 user 消息必须保留，保留消息的相对顺序不变。
3. 一条 assistant 消息若包含工具调用，它与这些调用的全部 tool 结果必须一起保留或一起删除；不能只留下调用或结果，也不能拆掉同一条 assistant 中的部分调用。
4. 超预算时按从旧到新的顺序删除可删除单元：普通消息是一单元；上述调用与结果整体是一单元，按 assistant 所在位置判断新旧。不得越过更旧的可删除单元优先删新的单元。无需优化信息价值或寻找最优组合。
5. 不能改写、截断任何单条消息。成功返回的消息确实符合预算，并报告删除了哪些输入位置、删除前后成本。
6. 如果删完允许删除的内容仍超预算，返回明确的“无法满足预算”结果和原因，不能默默删掉必保留消息，也不能把超预算结果标为成功。具体结果类型由你设计。

## 场景与取舍

至少考虑：本来就符合预算；旧普通消息过多；assistant 同时调用两个工具；旧工具返回超长结果；system 加最后一条 user 本身就超预算。

最后一条 user 之后的 assistant/tool 本轮不是必保留信息，仍按以上单元规则参与裁剪。这是刻意限定的策略，不表示真实产品都应如此。丢失信息必须能从删除报告中看出来。

不引入摘要模型、向量检索、tokenizer、文件存储、取消或新的 package。不要求先追踪 pi 的全部 compaction 流程。
