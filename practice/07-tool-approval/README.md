## 场景与选题依据

**业务场景**：Agent 协助用户修改一份笔记。其中，**读取操作**可直接放行；**覆盖写入**则必须先向用户展示拟写入的内容，等待用户批准或拒绝。在等待审批期间，用户随时可能点击“停止”取消运行；此外，上一轮残留的过期“同意”操作，绝不能误批下一轮的新请求。

**选题背景**：在实验 06 中，你已经证明了自己能够编写进程 runner、定义工具类型并完成封装，但当时的 Agent 接线、正式测试与解释校订主要由 AI 代劳。因此，本轮待验证的核心能力是：**根据业务需求自行选择框架接入点、设计跨越异步事件的审批状态，并独立完成端到端接线与验证**。（注：“待验证”仅代表尚未考察，不代表该项能力薄弱。）

相较于实验 06，本轮的核心管控对象变成了“尚未获准执行的工具调用”。你需要提供的新证据包括：

1. 审批机制能否真正拦截副作用（即实际的文件写入）。
2. 审批决策是否与特定请求严格绑定、互不串扰。
3. 你能否独立构建完整的集成测试证据。

_注：本实验无需重写进程执行器；即便实验 06 的复盘尚未补充完毕，也无需先“补考”，可直接开始本实验。_

## AI 预置的测试设施

[fixtures.ts](https://www.google.com/search?q=fixtures.ts) 中的 `createFixture(calls, initialText?)` 会创建一个独立的临时目录（初始笔记内容默认为 `原始笔记\n`），并对外提供以下设施：

- `tools`：包含 `read_note({})`（读取固定笔记）和 `write_note({ content: string })`（覆盖写入同一文件），均无需传入路径参数。
- `model` 与 `streamFn`：离线模拟模型。每次收到新 prompt 时，它会按 `calls` 列表的顺序依次发起一个工具调用；收到工具结果后返回固定的结束回答；若被取消，则输出合法的 `aborted` 响应。该模型不会自行决定批准、拒绝或重试。
- `notePath`、`snapshot()`、`executions`：分别用于获取真实文件路径、读取当前文件内容，以及查看工具实际进入 `execute` 阶段的执行记录。
- `requests` 与 `dispose()`：`requests` 记录模型每次收到的消息快照；`dispose()` 用于清理测试临时目录（**必须在 Agent 完全收尾后再调用**）。

其中，`calls` 数组中每一项的格式形如 `{ id: "call-1", name: "write_note", arguments: { content: "新笔记\n" } }`。每次 prompt 最多触发一次工具调用；当预设脚本耗尽后，模型将直接返回结束回答。这套设施直接复用了实验 05 的模型与消息构造逻辑，未引入任何新依赖。

## 待实现的接口与行为契约

请实现 `createApprovalSession({ fixture, onRequest })`。具体的 TypeScript 类型由你自行定义；在与 `pi` 对接的部分必须使用真实类型，**严禁使用 `any` 或类型断言（如 `as`）来掩盖接口不匹配**。内部代码如何拆分、采用何种状态机结构均由你自由决定。

### 返回对象结构

`createApprovalSession` 返回的对象需包含以下属性与方法：

- `agent`：真实的 `pi` Agent 实例，外部可直接调用其 `prompt`、`abort` 和 `waitForIdle` 方法。
- `pending`：当前无待审批项时为 `null`；处于等待审批状态时，返回当前请求的只读视图（至少包含 `requestId`、`toolCallId`、`toolName`、`path` 以及拟写入的 `content`）。其中 `requestId` 是审批请求的唯一标识，在同一个 session 生命周期内绝不可复用。
- `decide(requestId, decision): boolean`：用于提交审批决策。`decision` 的类型为 `{ kind: "approve" }` 或 `{ kind: "reject", reason: string }`。
- 当针对当前有效请求首次作出决定时，返回 `true`。
- 若传入的 `requestId` 未知、已作过决定或已被取消，则返回 `false`，且不得对其他请求产生任何副作用。

### 回调机制说明

每当产生新的审批请求时，系统应调用一次 `onRequest(request)`，供外部进行界面展示或测试事件同步。**必须保证在调用 `onRequest` 时，`pending` 状态已经就绪且可读。** 在本实验中，可假定该回调函数不会抛出异常、不会篡改请求对象，也不会在回调内部同步调用 `decide`。你无需实现任何终端交互界面或网页 UI。

### 核心行为契约

1. **只读直通**：调用 `read_note` 时无需审批，也不触发 `onRequest`；应直接读取原文件并生成正常的工具结果。
2. **写入拦截与等待**：调用 `write_note` 时，触发审批通知。在审批决定下达前，**严禁**进入工具的 `execute` 阶段，也**严禁**修改底层文件，当前 `prompt` 需保持挂起等待状态。通知中展示的路径与内容，必须与最终实际写入的目标完全一致。
3. **批准执行（Approve）**：有效的 `approve` 决策会让当前挂起的工具调用精确执行一次，将真实文件内容更新为所展示的内容。随后 Agent 收到成功的 `toolResult`，并正常结束本轮运行。
4. **拒绝执行（Reject）**：有效的 `reject` 决策不会调用写入工具，底层文件保持原样。Agent 会收到对应 `toolCallId` 的错误 `toolResult`（错误信息需包含拒绝理由 `reason`）。模型随后能读取到该错误结果并正常结束当前运行——**注意：“拒绝审批”属于正常的业务反馈，不等于调用 `agent.abort**`。
5. **等待期间取消（Abort）**：在收到审批通知后、作出决定前，若外部调用了 `agent.abort`，无需再调用 `decide` 即可直接结束当前的 `prompt` 和 `waitForIdle`。此时不得执行文件写入，文件保持原样，并生成对应的取消错误 `toolResult`。同时需清空 `pending` 状态并移除本次注册的取消监听器；此后若再对该请求调用 `decide`，应直接返回 `false`。
6. **请求严格隔离**：无论审批被同意、拒绝还是取消，`pending` 最终都必须重置为 `null`。同一个 Agent 实例支持后续再次发起 `prompt`。任何新的写入操作都必须重新发起审批——哪怕写入内容与上一次完全相同，也绝不能沿用历史决定。过期的 `requestId` 决策绝不能释放新的等待请求；**即使前后两次 `prompt` 中模型生成的 `toolCallId` 恰好相同，该隔离规则依然必须成立。**

### 边界与范围限定

上述契约即为本次验收的硬性边界，但不限制你的具体实现方式：

- **幂等与并发边界**：若对同一请求重复调用 `decide`，以首次被有效接收的决定为准。仅要求在“等待审批期间取消”时保证零写入，不要求回滚已经获准并开始执行的写入操作。测试用例中的“取消”与“决定”操作会有明确的先后顺序，无需处理同一毫秒内的极端竞态条件。
- **场景减负**：本实验限定为单 Agent、顺序执行 `prompt`、每次最多触发一个工具调用、参数合法且符合 Schema、操作单一固定临时文件，且无外部进程并发修改文件。**无需考虑**多审批并行、批次调度、跨进程状态恢复、审批超时、权限记忆（如“总是允许”）、接入真实大模型或构建真实 UI，也无需将工具扩展为支持任意路径的通用文件工具。
