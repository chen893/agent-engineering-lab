# 下一实验：有并发上限的任务调度

对应实践入口第 5 项，Q071。这里的 03 是本地第三次实验，不表示按入口编号推进。

模式：能力校准。AI 提供需求与最小接口，用户先整体设计和实现；测试可由 AI 编写，记录帮助程度。

## 为什么选择它

简单重试已通过，本次检验尚无证据的能力：多条异步路径共享状态、限制资源占用、区分启动顺序与完成顺序、隔离失败并正确收尾。它对应 Agent 批量工具调用或并行检索时的调度需求，但本次不接模型、不引入 Agent 框架，不假设独立工具可以随意并行。

## 需求

实现旁边 `concurrency.mts` 的 `runTasks(tasks, concurrency)`。

调用方传入一组尚未启动的任务函数。调度器最多同时运行 concurrency 个任务，返回与输入顺序一致的成功/失败结果数组。

1. 任务按输入顺序启动，每个任务恰好执行一次；完成顺序可以不同。
2. 活动任务数始终不超过上限；还有待启动任务且出现空位时就补入下一项，不等待同一批其他任务全部完成。可以利用 Promise，不要求精确毫秒调度。
3. 一个任务同步抛错或异步拒绝，都只影响自己的结果，不阻止其他任务。
4. 结果按输入顺序存放，保留成功值或原始错误；所有任务处理完才返回。
5. 空任务列表返回空数组。并发上限大于任务数量时正常运行。
6. concurrency 必须为正整数且有限；非法值导致返回的 Promise 拒绝，且不启动任何任务，即使任务列表为空也先验证配置。

为什么传函数而不是已启动的 Promise，是你需要能解释的接口选择。结果类型已提供，不要求记忆类型 API；调度结构和状态由你决定。

## 一个场景

| 输入位置 | 名称 | 启动后耗时（示意） | 结果 |
| --- | --- | --- | --- |
| 0 | A | 80ms | 成功，值 A |
| 1 | B | 10ms | 失败，错误 B |
| 2 | C | 30ms | 成功，值 C |
| 3 | D | 20ms | 成功，值 D |

concurrency=2。实现前先预测启动与完成顺序，以及 B 失败后哪个任务能开始。时间用于表达先后，不用把计时器的毫秒精度当成验收条件。

## 本轮边界和验证

只实现固定任务列表的并发调度。不加取消、重试、超时、动态入队或优先级，不拆类和多个模块。

AI 后续可用可控 Promise 验证：A 未完成时让 B 失败，观察 C 是否及时启动；随后以不同顺序完成任务，检查最大活动数、恰好一次执行、结果顺序和最终收尾。同步抛错、空列表与非法并发上限单独覆盖。无需真实网络和长时间 sleep。

可以直接运行代码文件中自己添加的场景：

```sh

```

文件当前只有接口占位，不会自动执行实验；不打印输出不代表通过。使用 .mts 明确 ESM，无需 package.json 或安装依赖。测试已在同目录 concurrency.test.mts，可从工作区根目录运行 `node --test practice/03-concurrency/concurrency.test.mts`。
